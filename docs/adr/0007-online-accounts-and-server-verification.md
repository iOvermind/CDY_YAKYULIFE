# ADR 0007: 線上化——帳號、伺服器重跑驗證，與設定覆蓋層

## Status

Accepted

## Context

成就與成就點數（AP）已經做完，但**沒有地方存**。`evaluateAchievements` 的
`unlocked` 參數目前永遠是空集合，因此每一局都重新結算一次，跨局的解鎖樹形同虛設。
天賦商店更是連做都不能做——買了東西沒有地方記。

同時，這個專案一路以來有一個沒有寫下來的前提：**純靜態、純本機**。它部署在
GitHub Pages，沒有 `src-tauri`，全專案零 `localStorage`、零 `fetch`。要有帳號就
必須推翻這個前提。

推翻它會帶出兩個新問題：

**信任。** 引擎跑在瀏覽器，因此「我這局拿了 40 AP」是客戶端說的。改一行
JavaScript 就能宣稱 999 AP。`CONTEXT.md` 的**重播日誌**與**簽章金鑰**兩條從
ADR 0002 就是為這一天寫的，但一直沒有使用者。

**天賦會改變模擬結果。** 天賦上限、衰老年份、受傷機率都是引擎的輸入，因此買了
天賦的人跑出來的人生與沒買的人不同。這讓驗證變得更棘手——伺服器必須知道那一局
帶著哪一組天賦，而天賦**可以退款**，「現在擁有什麼」與「那一局帶著什麼」是兩件事。

## Decision

**1. 做成線上版，前端與 API 同源。**

```
docker-compose
 ├─ app     Node：同一個 image 服務靜態前端與 /api
 ├─ db      PostgreSQL
 └─ tunnel  cloudflared → 自有網域
```

同源換到兩件事：**沒有 CORS**，以及 **token 可以放 HttpOnly cookie**——那是唯一
頁面上的 JavaScript 讀不到的存法，XSS 偷不走。

**不用 Redis。** 這個規模 Postgres 一個人吃得下；session 走 JWT 或一張表都行。
多一個 Redis 是多一個要顧的容器與一處狀態不一致的來源，換不到東西。

帳號：註冊即通過、不驗證、不可重複。密碼用 **argon2 或 bcrypt**——SHA-256 快到
可以暴力破解，不是密碼雜湊該用的東西。

**2. 伺服器重跑驗證，一開始就做。**

客戶端上傳重播日誌（種子＋選擇序列），伺服器用**同一份 TypeScript 引擎**重跑，
自己算成就與 AP。客戶端算出來的數字只是顯示，不是帳。

同一個 image 服務前端與 API，因此前端與伺服器端的引擎**永遠是同一份建置**——
ADR 0002 說「跨版本不保證重現」，這個架構讓那個風險不存在。

**3. 開局登記：凍結那一局的天賦組合。**

```
開局  POST /api/careers      → 伺服器凍結當下的天賦組合，回 career_id
結算  POST /api/careers/{id} → 用**凍結的那組**重跑，不是用玩家現在擁有的那組
```

天賦可以退款，沒有這道登記，一個中途退掉天賦的玩家會讓所有驗證失敗。

**4. 天賦走設定覆蓋層：宣告「改哪個設定、怎麼改、夾在哪」。**

```json
{ "path": "injury.chance.base", "op": "add", "value": -8, "min": 3 }
```

**新增一個天賦因此只是新增一筆 JSON**，不必改程式——與這個專案「所有平衡數字都在
JSON」的既有原則一致。代價是路徑寫錯不會在編譯期被抓到，因此配一條護欄測試：
每一個天賦的每一條路徑都必須解得到。

覆蓋層以**就地修改設定物件**的方式實作，在一局開始時套上、結束時還原。引擎各模組
在載入時就捕捉了設定物件的參考（`const cfg = season.pitching`），要改成傳遞式設定
等於重寫每一個模組。就地修改換到的是零重構，代價是**同一時間只能有一局套著覆蓋**
——瀏覽器本來就只跑一局，伺服器端的驗證則序列化處理。

**5. 天賦商店與參數編輯介面共用這一層。**

差別只在來源：天賦是官方的覆蓋，照常計分；編輯器是玩家自訂的，該局標記為
**自訂規則局**，不上天梯、不結算 AP（`CONTEXT.md` 既有的規則）。

## Considered Options

**帳號存在瀏覽器（localStorage）**——不必架伺服器。否決原因：「不能重複帳號」在本機
根本檢查不了，清一次瀏覽器資料就全部消失，而且要把密碼存在使用者讀得到的地方。

**信任客戶端回報的 AP**——最少的實作。否決原因：AP 是跨局累積且會換成永久強化的
貨幣，它一旦可以偽造，整個 Meta-progression 就沒有意義；而重播日誌早就存在，
驗證的成本遠低於它擋掉的東西。

**先信任、日後再補驗證**——可以早點上線。否決原因：資料格式會定型。沒有一開始就
存完整日誌的話，補驗證那天所有歷史資料都沒有價值。

**伺服器用「玩家現在擁有的天賦」重跑**——不必開局登記。否決原因：天賦可退款，這會
讓每一個退過款的玩家的歷史紀錄永久驗證失敗。

**天賦效果寫成具名的效果代碼**（`"effect": "injury_reduce"`）——型別安全，寫錯會被
編譯器抓到。否決原因：新增一種效果就要改程式，與「天賦商店要方便新增」的要求相反。
用護欄測試換型別安全。

**把設定改成傳遞式（每個函式收一份 config）**——沒有全域可變狀態，天生支援並行。
否決原因：那是把每一個引擎模組重寫一次，而換到的並行能力在這個規模用不到。

## Consequences

**正面**

- 成就與 AP 第一次有地方存，天賦商店因此做得起來。
- 重播日誌與簽章金鑰從「寫在文件裡的設計」變成真的在用的東西。
- 設定覆蓋層同時解掉參數編輯介面的前置條件——那條 ROADMAP 卡在「沒有覆蓋機制」
  很久了。
- 前端與伺服器同一份建置，跨版本重現的風險消失。

**負面**

- **這是這個專案最難回頭的決定。** 一旦有玩家的帳號資料，就不能說砍就砍——備份、
  遷移、隱私都變成長期責任。
- 多了一整條後端要維護：資料庫遷移、憑證、容器更新。
- **覆蓋層是全域可變狀態。** 同一時間只能有一局套著覆蓋，伺服器端的驗證必須序列化
  或隔離到獨立行程。這一條要寫在程式碼的顯眼處，否則日後有人加並行處理時會踩到。
- 天賦改變模擬結果，因此**分級分佈的校準基準只對「沒有天賦」的玩家成立**。老玩家的
  生涯會系統性地偏高，那是 Meta-progression 的本意，但校準腳本從此要註明它量的是
  哪一種玩家。
- 密碼、session、速率限制這些東西一旦做錯就是真的資安問題，而它們與棒球模擬完全
  無關——這條線之後，這個專案不再只是一個模擬器。
