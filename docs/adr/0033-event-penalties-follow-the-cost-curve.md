# ADR 0033: 事件扣點也走成本曲線

事件給的點數，**加與扣走同一條成本曲線**。一張「−3 點」的事件卡對能力 30 的球員
是掉 3 級，對能力 66 的球員是**借位**：退掉 65 → 66 那一級拿回 6 點，扣掉 3 點，
找零 3 點留在槽裡——`66 0/6` 變成 `65 3/6`。

老化衰退不在此列：`decline()` 仍是 1:1 直接砍能力值。

## 背景

`resolveEvent()` 產出的 `deltas` 兩邊不對稱。正的走 `#applyPoints()` → `train()`，
吃成本曲線；負的直接 `this.#ability[key] = Math.max(hard_floor, before + delta.points)`，
1:1 砍能力值。

於是同一張事件卡的上檔與下檔，在能力越高的地方差得越遠。能力 64 的球員：

*   `+3 點` → 那一級要 6 點，升 0 級，蓄力槽 3。畫面說「什麼也沒發生」。
*   `−3 點` → 直接掉 3 級。

**上檔要 6 點才買一級，下檔 1 點就砍一級——同一張卡片的兩隻手，一隻收批發價、一隻
付零售價。** 能力越高懲罰越重，而高能力正是玩家花了整個生涯堆上去的東西。事件卡的
文案寫著「+3／−3」，玩家有理由把它讀成對稱的賭注，實際上不是。

發現的路徑是使用者的體感：骰到直接加數值的事件時仍會遇到 `+4` 卻不動能力值的情況，
於是反過來問「那扣的時候呢，扣的也是蓄力嗎？」——不是，扣的是能力值本身。

## 決定

**新增 `untrain()`，作為 `train()` 的鏡像。** 點數先扣蓄力槽，扣不動就**退級找零**：
退掉的那一級退還**它自己的價錢**（`abilityCost(value - 1, ...)`），不是現在這一級的，
餘額留在槽裡繼續當存款。

`#applyPenalty()` 取代事件路徑上那行 `Math.max(hard_floor, before + points)`。

**蓄力槽永遠是正的。** 能力值與蓄力槽合起來是一條連續的點數座標，扣點就是往下走，
不夠就借位——就像十進位減法。曾經考慮讓槽變成負數（欠滿一級才掉），畫面上會出現
「66 −3/6」：能力值沒動、卻說你欠著債，而且能力仍照 66 結算，等於那 3 點在數值面
完全沒生效。借位把同一件事寫成「已經掉到 65，手上還剩 3 點」，看得見也算得到。

## 考慮過的選項

**維持 1:1 扣值，改成扣的時候也不吃曲線但加的時候吃。** 也就是現況。理由是「懲罰
就該痛」。否決：痛的分佈是反的——它讓低能力的新秀幾乎不痛（1 點 = 1 級，但他本來
就在便宜段，掉了也容易補回來），讓高能力的老將痛到不成比例，而那些能力是最貴、最
難重建的。這不是設計出來的難度曲線，是兩段程式碼各寫各的所產生的副作用。

**扣點也走曲線，但不留欠點——不夠退一級就當沒事。** 實作最省，畫面也乾淨。否決是
因為它讓懲罰在高能力段**可以被完全免疫**：能力 72 以上一級要 8 點，那麼所有 `−1`
到 `−7` 的事件對他等於不存在。玩家會學到「堆到 72 就不用怕事件」，這比原本的過重
更糟——過重至少還是個賭注，免疫則是把整類事件從遊戲裡刪掉。

**把事件卡的數字按能力段重新配平，程式不動。** 否決：那是拿資料去補一個結構性的
不對稱，每加一張卡都要重配一次，而且 `events.json` 的 `magnitude` 是全域倍率，本來
就不知道自己會落在哪一段能力上。

## 後果

*   **蓄力槽的定義不變**——仍是「未滿一級的餘數」，仍然只有正的。扣點的結果一律
    落在「能力值降一級 + 正的找零」上，`#poolPriceOf()`、`carryGauge()` 與畫面都
    不必處理負數這個分支。
*   **`ENGINE_VERSION` 滘到 3。** 同一份日誌重播會長出不同的生涯——按 ADR 0032 立下
    的規矩，這種「不會壞、只會安靜地不一樣」的改動一律滘版本。
*   **名人堂護欄從 21.8% 惡化到 30.3%（上限 12%）。** 這是預期中的：下檔變輕，球員
    守得住生涯末段的能力。按 ROADMAP「最後批次」的規矩**不當場調門檻**——規則還在
    動的時候調門檻是追移動靶。已記入該節待辦。
*   `decline()` 維持 1:1 且**刻意**維持。老化不是事件的賭注，它是時間本身，不該因為
    球員能力高就跑得慢；讓它吃曲線等於讓強者老得比較慢，那是另一個設計決定，不在
    這一份的範圍裡。
